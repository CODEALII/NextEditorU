# Testing and verification

## Automated offline checks

Run from the repository root:

```powershell
python -m unittest discover -s tests -v
python -m compileall -q worldstudio tests tools
python -m unittest tests.test_bfres_shader -v
```

Inspect a shader program's declared metadata from the local dump:

```powershell
python -m worldstudio inspect-shaders "NSMBU Modding Project/content/Common/shader/shaderfb.szs" --entry nw4f_cs_shader.sharcfb --program nw4f_cs_route_shader
python -m worldstudio inspect-shaders "NSMBU Modding Project/content/Common/shader/shaderfb.szs" --entry nw4f_cs_shader.sharcfb --program nw4f_cs_route_shader --json
```

The default output is a compact program/interface summary. `--json` prints the complete parsed metadata. Neither mode decodes GX2 instructions or proves the selected runtime variation. The viewer's expandable shader panel shows the material-option candidate and checked BFRES vertex-input bindings, including the original stored format and byte offset; these fields do not assign sampler UV behavior or decode unsupported vertex formats.

`tests.test_bfres_shader` includes a local W1 regression for the main grass shape's assigned program, material-option candidate, zero BFRES vertex-skin count, unresolved shape variation, declared sampler and vertex-input interfaces, base-color texture, and stored SRT. It skips local-resource tests when the user-supplied W1 or shader archives are unavailable. The viewer inspector prints the BFRES vertex-skin count and unresolved shape-specific macro names; a DOM regression checks these labels without mapping the count to an unsupported shader value. A pass verifies static resource metadata only, not the shader output in Cemu or on hardware.

The suite uses synthetic fixtures and, when present, the user-supplied files under `NSMBU Modding Project/`. Local game files are read in memory and are not included in exports or commits.

`python tools/cemu_preflight.py <isolated-profile> --expect-pack WorldStudioChain --graph-profile profiles/w1-core-progression.json` can optionally require that the packaged `CS_W1.szs` sidecar manifest records the same passing static graph profile and archive hash. Preflight still does not launch Cemu or verify movement.

`tools/cemu_input_test.py` accepts the same `--graph-profile` and `--compare-save-to` options. With `--graph-profile`, `--pack-file` is required; a mismatch writes a prelaunch result and does not start Cemu.

Each export manifest keeps the backward-compatible `changed_entries` list and adds an `entry_changes` record for every changed archive member, including source/output SHA-256 hashes, byte sizes and size delta. Profile-gated exports also record the normalized graph profile, its SHA-256, and a passed static-check marker; the archive-level hashes and `game_tested: false` remain explicit. The local export regression recomputes these values from the source and reopened output archive.

After exporting a saved project, run `python -m worldstudio verify-export <project.json> <export.szs>`. The verifier checks the output hash and path in the manifest, reimports the archive, compares its complete member list and contents with a fresh export from the project, and checks manifest fields and camera companion outputs. For a profile-gated export, pass the same profile with `--profile`; the verifier recalculates and compares that profile result. A success means the local package roundtrips consistently; it does not test Cemu or game behavior.

Saving changed native or OBJ-preview project content uses atomic per-file replacement to rotate the two most recent previous versions into adjacent `name.backup.json` and `name.backup-2.json` files. Both remain regular loadable projects, so they appear in the existing `*.json` picker; unchanged saves leave both backups untouched, and the status bar reports the newest backup path. The main project and each backup are replaced atomically as individual files; a multi-file rotation is not transactional if a later file operation fails. `test_overwriting_project_creates_openable_previous_version_backup` exercises native project reloads and rotation against the local source resource; the editor smoke test verifies the OBJ-preview save and status.

The Recent menu stores up to ten native-source/project paths and ten preview paths in a versioned JSON file under the user's local application settings. The lists are type-filtered, deduplicated by resolved path, and updated only after a successful open or save. `tests.test_recent_projects` covers ordering, deduplication, filtering, truncation, and malformed settings recovery; the editor smoke test checks native filtering and that canceling the unsaved-changes guard prevents a recent project from opening.

The native editor remembers the explicit static graph-profile choice in a separate per-user settings file keyed by the exact source archive SHA-256. On reopen, it reloads the profile only after bounded parsing and a world-prefix check; missing or mismatched profiles leave the export gate off and report why. Clearing the gate removes only the current archive's preference. `tests.test_graph_profile_preferences` covers hash binding, clearing, malformed/oversized files and invalid hashes; editor smoke tests cover selection, reopen restoration, wrong-world rejection and continued validation/export gating.

Edits to a native world opened from either an SZS source or saved JSON project are debounced into a checksummed per-user recovery snapshot (maximum 64 MiB), bound to the exact source-file path and hash. Saved lightweight-preview projects use the same flow. Reopening the source offers an explicit restore prompt; declining recovery, discarding unsaved edits, or successfully saving clears the snapshot. Recovery data stays outside the game archive. `tests.test_session_recovery` verifies project/kind/baseline binding, checksums, bounded size, and removal; Tk smoke tests exercise preview, native JSON, and direct-SZS restore plus discard behavior.

Check a directed route from a declared start to one or more required points:

```powershell
python -m worldstudio validate-graph --entry W101 --require W102 --require W103
```

Repeat `--entry` to allow multiple starts and `--require` for each required destination. To validate an edited saved project, pass its `.nws.json` file before these flags. Reachability follows the point table's normal and secret destination lists. The editor and export also use the same route checks: a newly added same-world destination must have a directed segment chain, and route edits must preserve chains that existed in the baseline. For changed single local destinations, an unambiguous linear BFRES macro-path list must form an ordered chain to the destination; branched legacy lists are skipped. Cross-world edges and pre-existing disconnected chains are not used as local route failures. Changed route segments must resolve endpoints in the current world; remote-world endpoints are left unresolved because their archive is outside the project. The check does not simulate unlock state, route movement, level loading or save persistence.

The checked-in `profiles/w1-core-progression.json` stores explicit W1 entry and required-location IDs in the versioned `nsmbu-world-graph-profile-v1` format. Run `python -m worldstudio validate-graph --profile profiles/w1-core-progression.json` to repeat the same static reachability check against the default local W1 archive, or add a saved `.nws.json` project before `--profile` to validate an edited project. Profiles are size-bounded, reject duplicate JSON keys and point IDs, and are matched to the source world's point-table prefix. `--profile` cannot be combined with `--entry` or `--require`. The checked-in profile is a chosen static test fixture; it does not assert game-side unlock or movement semantics.

After Cobra exports event scripts, `python tools/cobra_bridge.py catalog <scripts.txt> <version.json>` emits a JSON inventory of script IDs, priorities and numeric command IDs. This checks exported structure and optional registry membership only; it does not assign command behavior or connect scripts to point destinations or unlocks. `tests.test_cobra_bridge` covers malformed exports and checks the catalog counts against the local RPX export when the user-provided asset and Cobra checkout are available.

The native Add segment dialog lists unused route IDs found in the opened BFRES whose local endpoint bones resolve. IDs already present in point path fields appear first, and the status text says whether the ID occurs there. This match does not prove a route-table row is required by the engine. The dialog adds one CSV row using a road type observed in the source table; it does not edit point destination/path-chain fields. A structurally valid export containing such a draft does not prove that Mario can traverse it.

For a selected native point, `Edit order` opens an ordered picker for its normal or secret BFRES path-ID field. New entries are limited to IDs found in the loaded BFRES with resolvable local endpoints (remote-world endpoints remain unresolved); existing unknown values stay in the list unless explicitly removed. Applying without edits preserves the original field string exactly. Editing the list does not add route-table rows, set destinations, or establish runtime behavior.

OBJ import streams UTF-8 text and rejects files over 64 MiB, lines over 64 KiB, more than one million lines, more than 500,000 vertex/UV/normal records or attribute-split vertices, more than 200,000 faces, and more than 500,000 total face corners. Each face is limited to the ear-clipper's 1,024-corner ceiling; non-finite or out-of-range positions and UVs fail early. Baked-light `_u1` diagnostics still use a triangle BVH to inspect source UV projection; ambiguous/degenerate cases use the exact nearest-XZ-vertex tree. The project exporter keeps existing `_u1` values unchanged. Synthetic tests cover interior interpolation, edge projection, overlapping/degenerate fallback and bounded triangle checks. The import compatibility report surfaces ignored material libraries/assignments, vertex colors, smoothing groups, object/group boundaries and non-polygon geometry in the editor and CLI demo notes. Tests also exercise parser guards and parse the checked-in island OBJ (29 vertices, 54 triangles). Status text describes an experimental surface patch projected onto existing grass vertices, with preview import still available separately.

Saved table cells must be text; edited bone positions must target unique supported path-model bones and contain three finite coordinates within the BFRES export bound. ## Cemu integration checks

Follow [INTEGRATION.md](INTEGRATION.md) to prepare an isolated profile and preserve the original game tree and saves. Use the normal game resources as a baseline before enabling a generated graphic pack. Record the active pack, input profile, starting node, exact direction tested, destination shown, level result and save/reload result.

For the stock comparison, use `build/cemu-clean-baseline/launch.ps1` with the local RPX. Its separate MLC and settings enable CrashFix only. Check that profile's `log.txt` for the loaded RPX and active packs before testing. `build/cemu-island-baseline` is not a stock baseline: its current log shows World Studio Chain enabled.

For a controlled three-way movement comparison, use these isolated profiles in order: `cemu-clean-route-retest-20261021` (CrashFix only), `cemu-chain-route-retest-20261021` (point graph changed, existing BFRES paths retained), and `cemu-direct-route-retest-20261021` (direct route with BFRES bone rename). The preflight checks pack activation, archive hash, boot log, save snapshot, and keyboard configuration. It reads legacy `controller0.txt` or the installed Cemu profile's `controller0.xml`. `--require-keyboard` checks WASD on the left stick; add `--require-gamepad-a` for Z=A before a level-start test. At `Press 2!`, left-click inside the game window, wait for the map, then hold D from the recorded start node and note the destination. Add `--require-run` to require that the latest session loaded NSMBU v64 and activated the expected pack. The checker deliberately reports `gameplay_verified: false`; it cannot observe input, movement, level starts, progression or save behavior.

Do not treat a successful boot or rendered map as a traversal pass. Keep every export manifest's `game_tested` field false until route, level, progression, persistence and camera checks have actually been observed.
